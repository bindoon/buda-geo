# 运营复核报告模板（事实确认前必用）

复核报告是 `knowledge/` 的业务验收界面，不是运行摘要。读者不需要打开 JSON，便能看见“生成了什么、放在哪里、来自哪里、哪些仍是候选”。

## 生成前必读

逐项读取：

- `knowledge/company.baseinfo.json`
- `knowledge/company.profile.json`
- `knowledge/company.skus.json`
- `knowledge/company.evidence.json`
- `knowledge/company.facts.json`
- `knowledge/source-index.json`
- `knowledge/clean.overrides.json`
- `manifest.json`

若文件不存在，在报告中明确写“未生成”，不要跳过。

## 固定结构

```markdown
# 【{公司简称}】企业资料复核

**结论**：{可以提交确认 / 仍需修正后再确认}

## 1. 原始资料处理结果

| 原件 | 提取用途 | 处理结果 |
|---|---|---|
| {文件名} | {名片/介绍/产品/证据/客服参考} | {已解析/仅登记/忽略及原因} |

说明原件目录未修改，并给出产品图、企业图、证据图、隔离图数量。

## 2. 知识库文件与内容去向

| 产物 | 业务含义 | 本次实际生成内容 |
|---|---|---|
| `company.baseinfo.json` | 企业名片 | {公司、联系人、店铺、账号等数量/缺项} |
| `company.profile.json` | 企业介绍 | {五个分区实际是否有值} |
| `company.skus.json` | 产品库 | {产品数量、主产品、图片数量} |
| `company.evidence.json` | 证据台账 | {证据数量及范围} |
| `company.facts.json` | 可追溯事实与候选 | {事实数量、推断数量、冲突数量} |
| `source-index.json` | 原件索引 | {文件数量、隔离数量} |
| `clean.overrides.json` | 本项目语义清洗判断 | {图片分类、产品归并、字段规范化} |
| `manifest.json` | 闸门与缺失 | {当前状态、block/recommend/optional} |

## 3. 企业名片逐项复核

每个字段都列出；空值写“未提供”，禁止省略。

| 业务项 | 当前生成值 | 存放位置 | 来源与状态 |
|---|---|---|---|
| 公司全称 | {...} | 企业名片 | {原件提取/待确认归纳} |
| 公司简称 | {...} | 企业名片 | {...} |
| 联系人 | {...} | 企业名片 | {...} |
| 联系电话 | {...} | 企业名片/转化触点 | {...} |
| 地址 | {...} | 企业名片 | {...} |
| 地区 | {.../未提供} | 企业名片 | {...} |
| 官网或店铺 | {...} | 企业名片/转化触点 | {...} |
| 媒体账号 | {逐个平台列出} | 企业名片 | {...} |
| 密钥凭据 | {未保存/异常} | 不应进入知识库 | {...} |

## 4. 企业介绍逐段复核

按以下五个业务分区展示**当前生成的实际内容**，不能只写“已拆分”：

### 4.1 公司概况
{完整列出 intro；过长时按自然段列出，不得只给一句摘要}

### 4.2 产品与服务
{完整列出 products_services}

### 4.3 企业与供应链优势
{逐条列出 advantages 的全部业务点}

### 4.4 信任背书
{逐条列出 trust；注明哪些只有企业自述、哪些有证据支持}

### 4.5 客户与行业痛点
{逐条列出 pain_points；空时明确写未提供}

如当前值出现重复段落、残留标题、联系方式、孤立词、夸大表述或错桶，必须原样指出并列为待修正项；不能只在报告中美化后假装 JSON 已经正确。

## 5. 产品库逐项复核

对 `company.skus.json` 中**每个产品**重复一组，不得只列主产品：

- 产品名称、是否主产品、通用品类
- 卖点：逐条列出
- 属性：逐字段列出字段含义与当前值
- 企业能力：逐条列出
- 图片：数量、归档目录、来源范围；无需罗列所有稳定 ID
- 内容指令：是否关联、原件路径；说明它不是已确认企业事实
- 归并理由与待确认问题

## 6. 图片、证据与安全处理

- 按产品图、企业环境图、证据图、忽略图分别列数量和目录。
- 每条证据列出：名称/类型、支持哪些业务事实、不支持什么、披露范围、当前候选状态。
- 每个敏感或忽略文件单独说明原因；身份证不得显示姓名、号码或图片路径末端之外的内容。

## 7. 事实来源、归纳与冲突

- 列出从原件直接提取、Skill 归纳、运营规范化的数量。
- 所有 `inferred` / `operator` 业务值逐项转成人话列出，不能只报数量。
- 每个冲突列出原值、候选值、选择理由和是否仍需用户确认。
- 技术 ID、哈希、内部引用只放技术附录。

## 8. 缺失与质量问题

| 级别 | 内容 | 如何处理 | 是否影响确认 |
|---|---|---|---|
| 必须补 | {.../无} | {...} | {是/否} |
| 建议补 | {.../无} | {...} | 否 |
| 可选 | {.../无} | {...} | 否 |
| 清洗质量 | {重复、残片、错桶等/无} | {...} | {是/否} |

## 9. 当前状态与确认范围

- 结构、引用、语义、安全检查结果
- 当前是“可提交复核”还是“已确认”；二者不能混用
- 明确本次要求用户确认的字段范围
- 正式诊断尚未开始

## 请您确认

无 block 且无影响确认的清洗质量问题时，才请求用户回复：**“确认企业事实”**。

仅列 `app_id`、输入哈希、事实哈希、闸门状态和必要文件路径。
```

## 汇报原则

- 展示的是 JSON 中“当前已经生成的值”，不是期望值或二次润色稿。
- 把 `extracted` 说成“从原件直接提取”；把 `inferred` / `operator` 说成“待确认的归纳或规范化”。
- 长字段可以按自然段和业务点排版，但不得遗漏内容，不得用“已拆分”代替实际值。
- 空字段必须出现并写“未提供”，这样用户才知道是缺失，不是报告忘写。
- 不把事实 ID、source ID、JSON 键名堆进正文；用“企业名片、公司概况、产品与服务”等业务名称。
- 不汇报 clean 阶段未生成的关键词、问题库、FAQ、写文计划或配额。
- 无客服/询盘记录写“建议以后补，不影响企业事实确认”。
- CLI validate 通过不代表人读质量一定通过；发现重复、截断、孤立词或错桶时必须拦住确认。
- 有 block 或影响确认的清洗质量问题时，不请求确认，先说明怎么修。
- 用户确认后才运行 `geo-cli confirm-clean --project {PROJECT}`。
