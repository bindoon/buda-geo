## 1. 整体路径（更新：本地 JSON 先行，SaaS 只做同步落地）

再次调整顺序：**不先建线上数据库**。先在本地把全流程跑通，结构化数据以 JSON 格式落在本地；本地链路稳定后，再把 JSON 同步/写入到线上 SaaS，供客户查看。但从第一天起，本地的数据结构和鉴权方式就要按「未来是 SaaS 租户模式」来设计——用 `APP ID` 区分租户、预留 `Token` 校验位，这样以后同步上云时不需要重新设计数据结构，只是把本地 JSON 换成远程写入。

```
Step 0 本地 Agent + JSON 落地           Step 1 同步上云（SaaS 承接层）          Step 2 官网 & 服务器
────────────────────                ────────────────────                ────────────────────
知识库 A–F 清洗落 JSON：                 按 APP ID 同步上传、Token 登录         专属站点 HTML
基础信息 / 画像 / SKU+图               客户看知识库、发文、诊断周报            二级域名 → CNAME
场景词(品牌/搜索/问答/意图) / FAQ
→ 诊断命中 → 站外文 + 自媒体文
（结构预留 app_id，便于上云）
```

**关键设计原则**：
- **本地先行，SaaS 后补**：本地单机跑通一家客户的全流程（清洗、诊断、生成），落地为结构化 JSON 文件，不依赖任何线上数据库。跑通后再决定同步节奏（实时同步 or 定期批量同步）。
- **提前预留租户字段**：本地 JSON 的 schema 里从一开始就带 `app_id`（对应客户/租户标识），未来同步接口用 `app_id + token` 做鉴权和数据隔离，避免"先做单租户本地版，上云时再推倒重来"。
- **同步是单向的（本地 → 云）**：本地是生产/清洗的主战场，SaaS 只是"展示 + 存档"的承接层，不在云端做复杂业务逻辑运算。

### 2.1 Step 0 核心：知识库功能模块（要对齐做扎实）

知识库不是「一段公司介绍」，而是下面 **6 个子模块**。竞品荟信把 GEO 知识库拆成：`基础信息 → 画像设置 → 图片上传 → 视频上传 → 设置场景词 → 百科`；我们按紫驰工厂客户特点，合并/加强为下列能力（视频可后置）。

#### 模块 A · 公司基础信息（对应荟信 `baseinfo` + 信息收集表）

| 功能点 | 字段 / 能力 | 数据来源 | 验收标准 |
|--------|-------------|---------|----------|
| A1 主体身份 | 公司名称、简称、法人、注册地址、详细地址、创立日期、注册资金、企业类型、公司人数 | 信息收集表 + 营业执照 | 与执照一致；公司描述 ≥ 100 字 |
| A2 联系与触点 | 联系人、联系方式、座机；官网 / 1688 店铺 URL | 信息收集表 | 至少 1 个有效店铺或官网链接 |
| A3 主营与品牌 | 主营产品（与执照匹配）、品牌名称、产品单价区间 | 信息收集表 + 1688 | 不含敏感词/纯数字乱填 |
| A4 资质认证 | 营业执照、手持身份证、特殊资质（专利/认证等）电子件路径或 URL | 客户资料包 | 文件可回溯，本地 JSON 只存路径/哈希 |
| A5 媒体账号绑定表 | 百家号 / 知乎 / 抖音 / 头条号 / 搜狐号 等账号标识（密码不进知识库正文，单独密管） | 信息收集表「平台账号」区 | 账号字段齐全即可进入发文授权流程 |

**落地物**：`company.baseinfo.json`（含 `app_id`）。

#### 模块 B · 业务画像（对应荟信「画像设置」+ 信息收集表产品区 + 大泽「认识你」）

| 功能点 | 字段 / 能力 | 数据来源 | 验收标准 |
|--------|-------------|---------|----------|
| B1 核心业务文案 | 公司介绍（历史/厂房/年销/团队/设备/荣誉/售后/合作案例）、产品或服务描述、产品核心优势与应用 | 信息收集表 + 1688 详情 | 可直接喂给文章生成，无需再口述补洞 |
| B2 用户与行业痛点 | 需求满足 / 使用体验 / 供应链 / 技术等维度痛点 | 信息收集表 + 客服询盘高频问题 | 每条痛点能映射到至少 1 个场景词或 FAQ |
| B3 信任背书 | 证书、协会、专利、客户好评、客户案例、社会贡献、创始人介绍等 | 信息收集表 + 资质图 | 有「可核验」表述，避免空泛口号 |
| B4 创作方向配置 | 文案类型、创作方向、地区定向、内容调优备注（可选） | 运营配置 / 大泽「推广地区」 | 一篇文章生成时能读到明确方向参数 |
| B5 AI 一键装填 | 从 1688 / 已有资料自动起草画像，人工确认后落库 | Agent | 标杆客户从原始包 → 可确认草稿 ≤ 1 人日 |

**落地物**：`company.profile.json`（可多画像，默认一份主画像）。

#### 模块 C · 产品 SKU + 配图（对应荟信「图片上传」+ 1688 商品资产）

| 功能点 | 字段 / 能力 | 数据来源 | 验收标准 |
|--------|-------------|---------|----------|
| C1 SKU 结构化 | 商品名、规格/型号、类目、卖点、适用场景、价格带、链接 | 1688 商品 / 客户提供的 SKU 表 | 主力 SKU 全覆盖；字段可被文章模板引用 |
| C2 产品配图库 | 按产品名/SKU 分目录的图片；企业图、团队图、工厂图分桶 | 客户「1G 资料包」或信息收集表要求的图片文件夹 | 命名可关联 SKU；文章配图可自动抽取 |
| C3 图文绑定 | SKU ↔ 图片多对多；主图 / 细节图 / 场景图标签 | Agent 清洗 | 生成文章时「说到某 SKU 能带对图」 |
| C4（可选）视频素材索引 | 产品视频路径索引，不强制生成 | 客户视频 | 后期接短视频线时复用 |

**落地物**：`company.skus.json` + `assets/images/{sku_or_name}/...`。

> 紫驰优势：1688 店铺 SKU 与图片已在手上，清洗 Agent 应优先「链接/资料包 → 结构化」，而不是让客户手工一张张传。

#### 模块 D · 场景词 / 问答词包（要命中「用户问 AI 的那些话」）

这是 GEO 的命门。竞品逻辑：破足够多的问题词，确保其中一批能被 AI 命中推荐。荟信「设置场景词」拆成四类场景 +「训练词 → 蒸馏词」：

| 类型 | 含义（用户怎么问 AI） | 示例方向 | 我们要做的 |
|------|---------------------|----------|------------|
| **品牌场景** | 搜品牌/公司名相关 | 「XX 品牌靠谱吗」「XX 厂家」 | 绑定公司名、品牌名、别称 |
| **搜索词场景** | 品类/业务搜索 | 「推拉窗」「门窗安装」「环保哑铃」 | 对应信息收集表「3–5 个核心关键词 + 同品类拓展词」 |
| **问答词场景** | 对比/选型问法 | 「白噪音哪个好」「源头工厂哪家靠谱」 | 从询盘与行业问法生成，禁止空泛「十大」假问题 |
| **意图场景** | 用途/工况/采购意图 | 「跨境代发要什么资质」「OEM 贴牌出口文件」 | 从 1688 客服聊天高频意图提炼（紫驰差异化） |

配套能力：

| 功能点 | 说明 | 验收标准 |
|--------|------|----------|
| D1 主词 / 训练词录入 | 核心业务词 3–5 个起；拓展词必须同品类（表内示例：哑铃 → 环保/水泥/八角/包胶哑铃） | 与信息收集表一致，可人工改 |
| D2 拓词 / 蒸馏 | 前缀×主词×后缀组合；或模型蒸馏出候选词包（可参考竞品上限约 200 词/包） | 输出带类型标签的词表 JSON |
| D3 词包说明与地区策略 | 词包用途备注；训练词默认不含区域（区域另做定向） | 运营能分清「这包打什么」 |
| D4 命中目标设定 | 例如：诊断题库 N 题中，目标命中 M 题（竞品常见量级：破 1000 问、保 500 命中——具体数字与紫驰合同对齐） | 与模块 3 诊断打通，可复测 |
| D5 真问题优先 | 优先用买家真实问法（资质/代发/售后/交期），不用「保健品哪家好」类假问题 | 抽检词表，空泛问法占比低于约定阈值 |

**落地物**：`company.keywords.json`（按 `brand / search / qa / intent` 分类，含训练词、蒸馏词、来源、优先级）。

#### 模块 E · FAQ / 问答库（对应大泽 FAQ + 客服记录清洗）

| 功能点 | 说明 | 验收标准 |
|--------|------|----------|
| E1 异议类 FAQ | 基础异议、价格异议、效果异议、售后服务（大泽培训四类） | 每类至少若干条可发布答案 |
| E2 询盘意图 FAQ | 从客服聊天清洗：催付、发货、售后、出口资质、OEM/ODM 等 | 每条含「问法变体 + 标准答 + 关联 SKU/场景词」 |
| E3 分类入库 | 公司介绍 / 产品介绍 / 问答场景 / 数字员工话术等分类（可映射竞品「问答词」桶） | 文章生成与（可选）数字员工共用同一 FAQ |

**落地物**：`company.faq.json`。

#### 模块 F · 提示词与生成配置（知识库的「用法说明书」）

| 功能点 | 说明 |
|--------|------|
| F1 平台级提示词 | E-E-A-T 结构：公司介绍 + 综合优势 + 推荐理由 + FAQ |
| F2 词包×文类矩阵 | 场景词/问答词分别对应科普、测评、案例、排行榜、推荐、白皮书等（大泽内容类型） |
| F3 批量生成参数 | 单客户合同量级参考：诊断约 500 问、文章约 1500 篇（其中自媒体约 750）；支持「一次批量生成、再按日推送」以省 token |

**落地物**：`company.prompts.json` + `company.generation_plan.json`。

### 2.2 清洗 Agent 输入 → 输出（模块 2 工作流）

```
输入（紫驰已有优势）
├── GEO信息收集表.xlsx（基础信息、关键词、痛点、背书、平台账号）
├── 1688 店铺链接 / 商品与图片包
├── 客服聊天记录（询盘真问题）
└── 营业执照、资质、身份证等认证材料
        │
        ▼  本地清洗 Agent（Codex/Cursor Skill）
        │
输出（本地 JSON，均带 app_id）
├── company.baseinfo.json     # 模块 A
├── company.profile.json      # 模块 B
├── company.skus.json         # 模块 C
├── assets/images/...         # 模块 C 配图
├── company.keywords.json     # 模块 D（品牌/搜索/问答/意图）
├── company.faq.json          # 模块 E
└── company.prompts.json      # 模块 F
        │
        ▼  人工确认（群内或本地预览）→ 进入诊断 / 写文章
```

标准作业节奏（对齐大泽签单后流程，供内部交付参考）：资料齐全后第二个工作日起服务；约 10–14 个工作日可见推荐效果——自研链路应用同一 SLA 做验收对照。

## 2.7 Step 0 本地开发过程：Skill 分步路由 + Tool/API

> 这一节记录**怎么在本地把链路跑通**，不是报价。目标形态：一个总 Skill（暂名 `zichi-geo`）+ 若干 references 文档 + 可执行 Tool/CLI；Agent 根据当前输入**路由到对应分支**，按步骤产出，人工确认后再进下一步。

### 2.7.1 总体形态

```
用户 / 运营在 Cursor 里丢材料或下指令
              │
              ▼
     ┌─────────────────┐
     │  Skill 入口路由器 │  识别：现在手里是什么？要做哪一步？
     └────────┬────────┘
              │
    ┌─────────┼─────────┬──────────┬──────────┐
    ▼         ▼         ▼          ▼          ▼
  clean     diagnose   write     publish    sync*
 企业清洗    诊断报告   文章生成   GEO发布    上云(Step1)
    │         │         │          │
    ▼         ▼         ▼          ▼
```

### 2.7.2 路由规则（Skill 第一步必做）

Agent 读完 `SKILL.md` 后，先判定分支，再加载对应 `references/`，**禁止**未路由就通读所有文档或跳步写文章。

| 用户输入 / 当前状态 | 路由分支 | 加载文档 | 下一步产出 |
|---------------------|----------|----------|------------|
| 信息收集表 Excel、1688 链接、客服聊天、图片包、营业执照 | **`clean`** | `clean-enterprise.md` + `schema-knowledge.md` | `company.*.json` + `assets/` |
| 企业事实已确认，说「做诊断 / 测可见度 / 出报告」 | **`diagnose`** | `diagnose-baseline.md` | 基线报告 + diagnosis gaps |
| 诊断已确认，说「关键词 / 场景词 / 用户怎么问」 | **`scenarios`** | `build-demand-scenarios.md` | confirmed scenario library |
| 说「导出大泽 / 摘星 / 掌心格式」 | **`platform-export`** | `export-platform-views.md` | 可追溯平台视图 |
| 场景已确认，说「选题 / Prompt / 写作计划」 | **`plan`** | `plan-content.md` | confirmed content plan |
| 计划已确认，说「写文章 / 批量生成」 | **`generate`** | `generate-articles.md` | `articles/*.md` 草稿 |
| 草稿待审，说「审稿 / 批准」 | **`review`** | `review-articles.md` | approved 稿件 |
| 稿件已批准，说「发布 / 投出去」 | **`publish`** | `publish-articles.md` | 发布回执 / 链接 / 失败重试列表 |
| 说「复测 / 下一轮优化」 | **`measure`** | `measure-and-iterate.md` | 新缺口与迭代计划 |
| 本地全套已稳，说「同步上云」 | **`sync`** | `sync-saas.md` | SaaS 同步回执 |
| 模糊（只丢一堆文件没说要干嘛） | 先问一句 | — | 「先清洗知识库，还是已有 JSON 直接诊断/写文？」 |

闸门（每步结束必须停）：

1. **clean 后**：人工确认企业事实（缺字段列表 + 预览），确认前不进入 diagnose。
2. **diagnose 后**：人工确认诊断报告，才能生成场景库。
3. **scenarios / plan 后**：分别确认场景版本与内容计划，才能生成草稿。
4. **generate 后**：所有公开稿件必须人工审稿批准后再 publish。
5. **publish 后**：回填链接/截图路径，供复测与周报使用。

### 2.7.3 分支一：`clean` — 企业数据清洗

**触发**：拿到企业原始资料（对应模块 A–E）。

**Skill 内步骤**（写进 `clean-enterprise.md`）：

1. 识别输入类型：Excel 信息收集表 / 1688 / 聊天记录 / 图片目录 / 混装 zip。  
2. 按模块装填：A 基础信息 → B 画像 → C SKU+图 → D 场景词 → E FAQ（可多轮，缺什么补什么）。  
3. 严格按 `schema-knowledge.md` 落盘，带 `app_id`。  
4. 输出「缺失字段清单」给运营，而不是静默空字段。

**格式约定**（schema 文档必须写死，示例级）：

| 文件 | 用途 |
|------|------|
| `company.baseinfo.json` | 模块 A |
| `company.profile.json` | 模块 B |
| `company.skus.json` | 模块 C |
| `company.keywords.json` | 模块 D（`brand/search/qa/intent`） |
| `company.faq.json` | 模块 E |
| `company.prompts.json` | 模块 F |
| `assets/images/...` | 配图，文件名可关联 SKU |
| `manifest.json` | 本客户进度：哪步完成、谁确认、时间戳 |

清洗以 **Skill + 模型** 为主；若后续有 1688 抓取脚本，再挂到 `tools/`，由 `clean-enterprise.md` 标明何时调用。

### 2.7.4 分支二：`diagnose` — 诊断报告（要提供接口）

**触发**：知识库已确认，要测「AI 里有没有你」。

**Skill 内步骤**（`diagnose-baseline.md`）：

1. 从 `company.keywords.json` + FAQ 生成 / 抽样检测题。  
2. **调用诊断 Tool/API**（本地 CLI 封装，不在对话里手搓请求）。  
3. 汇总命中、未命中、竞品露出 → 写 `diagnosis.report.json` + Markdown/PDF 可读版。  
4. 把「未命中词」回推给运营：补 D 词包或先发哪类文。

**接口层（开发要交付的）**：

| 能力 | 说明 | 形态 |
|------|------|------|
| 可见度探测 | 按问题打豆包 / DeepSeek 等，解析是否露出品牌/公司 | `tools/... diagnose run --app-id X --platforms doubao,deepseek` |
| 快照/凭证 | 保存回答摘要或截图路径，供客户感知 | 回执写入 `diagnosis/snapshots/` |
| 评分汇总 | 透明指标 + 分平台明细 | JSON 字段约定在 `diagnose-baseline.md` |

首期允许：CLI 内先接「已有第三方 GEO 诊断 API」或半自动（脚本提问 + 人工贴结果）；但 **Skill 调用方式要先固定**，避免每家客户换一套手工流程。

### 2.7.5 内容计划、文章生成与审稿

**触发**：知识库就绪；通常诊断后更清楚优先词。

**Skill 内步骤**（分见 `plan-content.md`、`generate-articles.md`、`review-articles.md`）：

| 规则块 | 内容 |
|--------|------|
| 输入绑定 | 必须引用哪些 JSON（禁止脱离知识库空写） |
| 线路分流 | **站外批量** vs **自媒体精品**（提示词严度、审核强度不同） |
| 结构模板 | E-E-A-T：介绍 + 优势 + 推荐理由 + FAQ；大泽类：科普/测评/案例/榜单/推荐等 |
| 词包用法 | 品牌/搜索/问答/意图如何进标题与正文；真问题优先，禁空泛「十大」 |
| 配图规则 | 优先 SKU/企业实图；命名与插入位置 |
| 去重与风控 | 同客多篇差异、敏感行业禁写（对齐大泽禁止行业） |
| 批量参数 | 一次生成数量、文件命名、`articles/queue.json` 队列格式 |
| 质量下限 | 站外可宽松但不可垃圾；自媒体错别字/图文必人工 |

产出：`articles/{channel}/{date_or_batch}/*.md` + 元数据（关联 keyword 类型、SKU、是否已审）。

文章生成可以主要靠 Skill+模型；若要省 token 做「千篇批量」，再加 `tools/... generate batch`。

### 2.7.6 分支四：`publish` — 第三方 GEO API 发布

**触发**：稿件已审（自媒体）或站外队列已确认。

**Skill 内步骤**（`publish-articles.md`）：

1. 读队列：待发平台、账号绑定（来自 baseinfo 媒体账号表，密钥走环境变量/密管）。  
2. **调用第三方 GEO / 媒体发布 API**（封装进 Tool，Skill 只写「调用哪条命令、传哪些字段」）。  
3. 记录回执：平台、URL、状态、失败原因、可重试。  
4. 更新 `manifest.json` 与发文周报素材。

**平台映射（与信息收集表 / 竞品发布侧对齐，接口以实际签约供应商为准）**：

| 渠道类型 | 示例平台 | 发布方式（本地阶段） |
|----------|----------|----------------------|
| 自媒体 | 百家号、头条号、抖音图文、知乎、搜狐号、公众号 | 优先第三方 GEO 聚合 API；无 API 则人工/半自动，回执仍按同一 JSON 记 |
| 第三方商业/新闻 | B2B 站、新闻媒体 | GEO 服务商下单 API 或人工采购，同样写回执 |
| 自有信源 | 后续 GEO 官网 | Step 2；本地先可生成 HTML 不发布 |

开发要点：

- **密钥与账号**：不进客户知识库明文；`PUBLISH_API_KEY` / 分平台 token 放本地 env。  
- **幂等**：同一 `article_id + platform` 重复提交不双发。  
- **失败可观测**：Skill 要求输出失败列表，而不是只说「发布完成」。

> 与第 2.0 表「模块 9」的关系：模块 9 是「自建/多供应商深度对接」的产品项；**本地 Step 0 就必须先有一层 publish Tool**，哪怕先只接一家 GEO API，否则链路在「写完」断掉，无法端到端验收。

## 6. 待确认 / 待补充事项

以下是目前方案里还不够细致、需要和紫驰进一步对齐的点：

- **本地 → 云同步的节奏未定**：跑通本地全流程后，是实时同步还是定期批量同步到 SaaS，需要和紫驰确认客户查看数据的时效性要求。
- **多租户扩展节点未定**：本次先按单机单租户（本地一次跑一家、云端用 `app_id` 隔离）开发，没有明确"什么时候、什么条件下"升级为本地也能并行跑多租户（比如客户数到多少、或验证周期多长后升级）。
- **服务器预算与归属**：Step 2 需要新增服务器承载官网 HTML 和域名解析，具体规格、云厂商、费用由谁承担（算入开发费还是单独走紫驰的运维预算）待定。
- **数据安全与保密条款**：涉及客户 1688 店铺信息、客服聊天记录等相对敏感的数据，需要在合作协议里明确数据使用边界、留存方式、是否需要脱敏处理（尤其是本地 JSON 落地阶段数据存放在谁的机器上）。
- **诊断报告的呈现载体**：诊断先在本地跑通验证，同步上云后，报告最终是在 SaaS 页面展示、导出 PDF、还是继续本地生成给客户看，还没最终定。
- **站外文章"随便出"的质量下限**：虽然站外线要求相对宽松，但仍需要一个最低质量标准（避免被平台判定为垃圾内容拖累整体权重），这个下限需要和紫驰对齐。
- **里程碑与验收节点**：分成条款里提到的"效率/质量基准"目前只是方向性描述，需要落成具体可验收的指标（如可见度评分提升幅度、单客户边际成本目标值、发文数量/周期）。
- **场景词四类的词量配比**：品牌 / 搜索 / 问答 / 意图各占多少、蒸馏词上限、与诊断题库如何抽样，需和紫驰运营定一版默认策略。
- **SKU 粒度**：是「主力 SKU 精做」还是「店铺全量 SKU 入库」；影响清洗工时与配图存储。
- **荟信字段是否 1:1 对齐**：基础信息里执照级字段（法人、注册资金、多级产品分类等）工厂客户是否值得全收，还是先收信息收集表那一档精简集。
- **诊断 API 供应商**：自建探测 vs 复用大泽/荟信/其他 GEO 诊断接口；本地 CLI 的对接对象要尽早定。
- **发布 API 供应商与权限**：第三方 GEO 聚合发文 API 的账号、费率、支持平台列表；无 API 的平台是否接受「半自动 + 统一回执格式」。
- **Skill 仓库位置**：`skills/zichi-geo` 是放 myskills 私有仓，还是单独给紫驰的交付仓（影响分成后的代码归属表述）。
